This document is the state of the work: what was changed, what is proven,

## 0. TL;DR

Four user-facing problems:

1. `rdar:45025538` banner in the status bar.
2. Settings opens then gets killed.
3. No Appearance / dark-mode control in Control Center.
4. Low-resolution rendering made the UI **bigger** instead of smaller.

The current design: render at 720x1520, double every pixel 2:1 in the CPU
bridge into the 1440x3040 panel, and tell UIKit the logical screen is
360x760 pt (`display-scale=2`). That keeps UI size identical to a 1440px
@4x-ish layout while touching only half as many pixels.

The banner fix required three iterations. The first swizzle targeted
`_UIStatusBarVisualProvider_*` (UIKit) but SpringBoard uses its own
`STUIStatusBarVisualProvider_*` overrides, so nothing changed. The second
version had a latent infinite-recursion path (see §3.5). The current commit
answers the lookup directly and never chains to the original.

Settings was killed by the 19.58 s scene-create watchdog while SwiftUI
looped in layout; the likely trigger was the old 240x506.67 pt screen
(fractional height). The scale fix should remove it, but this is not yet
proven on device.

Control Center's Appearance module is seeded into
`ModuleConfiguration.plist` at boot by the system-app bootstrap. Also not
yet visually confirmed.

## 1. Hardware and boot layout

- Phone: Samsung Galaxy S10+ `beyond2lte` / SM-G975F, serial `R58M45TCCYE`.
- TWRP: 3.7.0_9-2, adb in `recovery`.
- Partitions used:
  - `sda14` = BOOT (only partition flashed in this work)
  - `sda25` = SYSTEM
  - `sda31` = USERDATA — **the iOS root lives here** (HFS+), not on SYSTEM.
- The boot.img layout is: Android boot header + 4 MiB UEFI FD in the
  "android kernel" slot (contains Mu UEFI + embedded `XnuLoader.efi`) +
  XNU Mach-O payload. So flashing BOOT also updates the loader/device tree,
  including `display-scale`.
- iOS is 26.6.2 build 23G90. The runtime compat gate also accepts 25F71.
- iOS sees the device as `iPhone17,2` / "iPhone 16 Pro Max" with
  `artwork-device-subtype 2868`, `artwork-scale-factor 2`.

### Display pipeline

```
UIKit 360x760 pt
  -> compositor renders 720x1520 (half linear resolution)
  -> CPU nearest-neighbour 2:1 bridge
  -> scanout 1440x3040 (panel native)
```

Relevant files:

- `uefi/XnuLoader/DeviceTree.c:87-91` — `display-scale = 2`
- `uefi/XnuLoader/DeviceTree.c:135-139` — `artwork-scale-factor = 2`

## 3. What was changed and why

### 3.1 Charging (already working)

`xnu-overlay/iokit/Kernel/arm/B2LPower.cpp`

- MAX77705 charger at 0x69; `CHG_INT_OK` (0xB2) bit 6 = `CHGIN_OK`.
- Bit 1 (`DISQBAT_OK`) is set even without a cable, so it must not be used
  as "charger present".
- Fix masks `0x40` (`CHGIN_OK_MASK`). Charging was visually confirmed.

### 3.2 Half-resolution rendering

`9ca7f35`, `dde66e7`.

- Render surface is 720x1520 instead of 1440x3040.
- `B2LBlit` supports 4/3 and 2/1 nearest-neighbour bridges; the scanout path
  uses 2/1.
- If the reduced surface cannot be created, it falls back to full size.
- Surface properties were confirmed on device as 720x1520.

### 3.3 Logical size / MobileGestalt

Problem: with `display-scale=3` the 720px screen became 240x506.67 pt. That
is both "UI even bigger" and a fractional height, which trips SwiftUI layout.

Fix:

- `display-scale=2`, `artwork-scale-factor=2` → 360x760 pt.
- The 360 pt width is exactly the 1080px @3x profile.

MobileGestalt caches screen geometry. `b2l_profile_cache_refresh` in
`xnu-overlay/bsd/kern/b2l_profile_cache.h` renames the cache to a backup
once. The old code used a `-v2` backup name and the device already had that
backup, so the function returned early and the stale cache survived — this
is why the `4d26581` boot still had scale 3 and a huge UI.

`5502192` changes the backup to

```
/private/var/containers/Shared/SystemGroup/systemgroup.com.apple.mobilegestaltcache/Library/Caches/com.apple.MobileGestalt.b2l-before-profile-v3.plist
```

so the next boot on that kernel regenerates the cache once from the device
tree.

### 3.4 Settings watchdog

Crash report evidence: `Preferences-2026-11-21-152203.ips`, pid 869, uptime
640 s.

- `scene-create watchdog transgression`, 19.58 s, 89% CPU
- Main thread inside SwiftUI/UIKit layout:
  `preferredLayoutAttributesFitting` → `sizeThatFits` → AttributeGraph
  recursion
- It is a watchdog kill, not a crash.

The dyld cache in `/home/nottelling/dyld-os` matches the device UUID
`CC670B30-8FDB-34DA-AFAB-7AEE1251384B`, so that crash was symbolised
accurately.

Primary hypothesis: the fractional 506.67 pt height / wrong scale caused
the layout loop; the scale fix should resolve it. **Unverified on device.**

### 3.5 Status bar `rdar:45025538` banner

UIKit selects a status-bar visual provider by matching the screen against
known iPhone profiles. A 720px render matches none, so it installs a
Fallback provider that logs:

```
No status bar visual provider for screen ... Please see rdar://45025538.
```

SpringBoard has its own `STUIStatusBarVisualProvider_*` classes which
override `+visualProviderSubclassForScreen:visualProviderInfo:`. Swizzling
only UIKit's `_UIStatusBarVisualProvider_*` copies had no effect.

Current fix in `userspace/graphics-compat.m`:

- Swizzle the class method on every class that **directly implements** it:
  `STUIStatusBarVisualProvider_{Split,Phone,iOS,DynamicSplit}` and the
  `_UI...` equivalents.
- Return `STUIStatusBarVisualProvider_Split1080` (SpringBoard receiver) or
  `_UIStatusBarVisualProvider_Split1080` (UIKit receiver).
  `1080 / 3 = 360 pt`, exactly this panel's logical width.
- **Never call the original.** A subclass forwarding with `[super ...]`
  keeps the original receiver, so a per-receiver original pointer could
  re-enter the override forever. `12c5897` removed that chaining.
- Breadcrumb fallback: swizzle
  `-[SBDeviceApplicationSceneStatusBarBreadcrumbProvider breadcrumbTitle]`
  and `-[UIStatusBarBreadcrumbItemView setDestinationText:]` to drop any
  text containing `rdar` (case-insensitive). Real breadcrumbs keep working.
- A second `AMFI 0x5b` beacon is emitted after both installs. Two
  `B2L COMPAT: injected compatibility library constructor ran in
  SpringBoard[pid]` lines prove the enabled path ran; one line means the
  dylib loaded but `b2lRuntimeMode()` returned false.

Forensics: the literal `rdar:45025538` does **not** exist in the dyld shared
cache, SpringBoard.app (its on-disk executable is a 133 KB stub), UIKitCore,
SpringBoard.framework, SpringBoardFoundation, or UIKitServices resources
(searched ASCII and UTF-16). Only the log string
`Please see rdar://45025538.` exists, in the cache. So the text is almost
certainly produced by the Fallback-provider path rather than read from a
strings table.

### 3.6 Control Center Appearance / dark mode

- Bundle exists: `/System/Library/ControlCenter/Bundles/AppearanceModule.bundle`
  (`com.apple.control-center.AppearanceModule`, principal class
  `CUAppearanceModule`, MinimumOSVersion 26.6, arm64e).
- It is in `ModuleAllowedList.plist`, but the shipped
  `ModuleConfiguration.plist` only listed six modules.
- `userspace/system-app-bootstrap.m` `ensureAppearanceModule()` rewrites
  `/private/var/mobile/Library/ControlCenter/ModuleConfiguration.plist`:
  appends the identifier to `module-identifiers`, removes it from
  `disabled-module-identifiers`, sets `version`/`userenabled-fixed...` if
  missing, and chowns to 501:501 mode 0644.
- This runs before the migration receipt check, so it repeats every boot.
- `ControlsIconState.plist` on the device was empty (`buttonBar: []`,
  `iconLists: [[]]`). Unclear yet whether the gallery needs an entry there
  or in `DefaultModuleSettings.plist`; check the gallery visually first.

cd /home/nottelling/beyond2lte-flash

Fallback if something goes wrong:

```bash
./restore-boot.sh          # or the image in b2l-backups
```

Only BOOT is touched. Do not reflash SYSTEM/USERDATA.

## 7. Post-flash verification checklist

After iOS boots (give it several minutes; SpringBoard + first SwiftUI layout
are slow):

1. **Banner**: status bar shows no `rdar:45025538` / `rdar://45025538`.
2. **UI size**: layout is 360x760 pt — same apparent size as the old
   working UI, not oversized. Status bar text is not clipped.
3. **Settings**: open Settings, leave it 60+ s, open a sub-page
   (e.g. Display & Brightness), return. It must not disappear.
4. **Control Center**: open CC, enter edit/gallery, confirm an
   Appearance/Dark Mode control can be added; toggle it.
5. **Charging**: plug/unplug, verify the battery icon/charging state.
6. **Regressions**: home screen icons/wallpaper scale, lock screen,
   app switcher, rotation (if supported), touch.

Record a screenshot if possible; text scale is the fastest way to confirm
`display-scale=2` took effect.

## 9. Failure playbook

### Banner still visible

1. Confirm both AMFI beacons in SpringBoard → the dylib ran and the swizzle
   block executed.
2. Check unified log for `status bar provider override installed on
   STUIStatusBarVisualProvider_...`. If no such line, `objc_getClass` found
   no class with a direct implementation (unexpected) or the dylib did not
   load.
3. Try the UIKit override key instead (belt and braces):
   write `UIStatusBarVisualProviderClassName =
   STUIStatusBarVisualProvider_Split1080` into
   `/private/var/mobile/Library/Preferences/com.apple.springboard.plist`.
   This is the key UIKit's own warning
   (`WARNING: Using overridden status bar visual provider class: %@`)
   refers to; adding it to `ensureAppearanceModule()`-style bootstrap code
   is safer than editing prefs by hand.
4. If text comes from the breadcrumb item, the `rdar` filter should already
   drop it. If not, log `destinationText`/`breadcrumbTitle` values to find
   the actual source.

### Settings still disappears

1. Pull the newest `Preferences-*.ips`; check whether it is again
   `scene-create watchdog transgression` and the stack.
2. Confirm the screen size in the log/plist:
   MobileGestalt `UserInterfaceIdiom`/display keys, or a diagnostic
   `NSLog` of `[UIScreen mainScreen].bounds` and `.scale`.
3. If the size is correct and the layout loop persists, the next lever is
   the launchd watchdog: removing watchdogd from the derived launch cache.
   **Important:** that derived cache is only built with
   `build_userspace=true`; a BOOT-only flash does not apply it.
4. Reducing logical size further (e.g. `display-scale` 3 with 1080px
   render) is not desirable; it reintroduces fractional/large UI.

### Appearance control missing

1. Read back `/private/var/mobile/Library/ControlCenter/ModuleConfiguration.plist`
   and confirm the identifier is present and not disabled.
2. Check the unified log for the bootstrap line. If the bootstrap did not
   run, verify its marker/lock and boot args.
3. If the gallery does not list it, inspect
   `/System/Library/ControlCenter/Bundles/AppearanceModule.bundle/Info.plist`
   and Control Center's other plists (`DefaultModuleSettings.plist`,
   `ModuleAllowedList.plist`, `ControlsIconState.plist`) and mirror the
   entries of a module that does appear.
